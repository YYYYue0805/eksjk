# 需求文档 — EKSJK V2 全栈重构项目

## 引言

EKSJK（儿科生长发育数据管理系统）是一个面向医疗健康领域的全栈应用，专注于儿童内分泌疾病的临床数据管理、患者随访跟踪、生长发育监测和医学影像处理。

本次重构计划对**前后端代码进行彻底重构**，保留原有的全部业务功能，同时在架构、性能、安全性、可维护性和用户体验方面进行全面升级。重构范围涵盖：

- **后端**：从 Python Django 迁移至 Java Spring Boot 3.x，采用 MyBatis-Plus ORM、Sa-Token 认证授权
- **PC 端前端**：从 Vue 2 + Element UI 迁移至 Vue 3 + Element Plus，采用现代化三栏布局，简化数据录入，提升检索效率
- **微信小程序家长端**：采用 uni-app (Vue 3) 重新开发，提供便捷的儿童生长数据录入和健康管理
- **微信小程序医生端**（新增）：采用 uni-app (Vue 3) 独立开发，为医生提供移动化的患者管理和随访跟踪能力

> ⚠️ **重要约束：** V1 旧项目（`eksjk_v1` 目录）的代码保持不变，不做任何修改。V1 仅作为业务逻辑参考，所有新代码均在 `eksjk_v2` 目录下独立开发。

### 部署架构

- 前后端分离：PC 端前端构建为静态资源，后端提供 RESTful API
- PC 端前端通过 Nginx 托管，API 请求反向代理至 Spring Boot 服务
- 微信小程序（家长端和医生端）通过微信开发者工具构建并上传至微信公众平台，审核后发布
- 配置通过本地 `application-prod.yml` 管理，无需外部配置中心
- PC 端用户通过浏览器直接访问，家长端用户通过微信扫码/搜索进入小程序，医生端用户通过独立的医生版小程序入口访问

## V1 前端问题分析（重构动因）

| 问题类别 | V1 现状 | V2 改进方向 |
|---------|---------|------------|
| 布局结构 | 无标准布局框架，功能入口散落在顶部按钮和下拉菜单中 | 经典侧边栏 + 顶栏 + 内容区三栏布局 |
| 路由组织 | 所有页面平铺在一级路由，无嵌套布局 | 嵌套路由 + 布局组件，支持面包屑导航 |
| 搜索体验 | 搜索条件水平排列，无折叠/展开，无快捷搜索 | 搜索条件折叠/展开、回车即搜 |
| 表单组件 | 单个疾病表单组件超过 100KB，代码臃肿难维护 | 大表单拆分为多个子组件，分区/分步录入 |
| 数据录入 | 表单字段平铺，无分组，录入效率低 | 按业务分区，支持智能默认值和输入联动 |
| 导航效率 | 需先选择疾病类型再进入列表，操作路径长 | 侧边栏直接展示疾病类型菜单，一键切换 |

## 阶段一：基础设施搭建

> **目标**：搭建前后端项目骨架，建立统一的开发规范和基础设施。
> **前置依赖**：无

### 需求 1：后端项目基础架构搭建

**用户故事：** 作为一名开发者，我希望有一个结构清晰、规范的 Java 后端项目骨架，以便能够高效地进行后续功能模块的开发。

#### 验收标准

1. WHEN 项目初始化 THEN 系统 SHALL 基于 Spring Boot 3.x + JDK 21 创建 Maven 多模块项目，包含以下模块：
   - `eksjk-common`：公共工具类、常量定义、通用异常
   - `eksjk-model`：数据模型（Entity、DTO、VO）
   - `eksjk-mapper`：MyBatis-Plus Mapper 接口和 XML 映射文件
   - `eksjk-service`：业务逻辑层
   - `eksjk-web`：Controller 层 + Spring Boot 启动类
2. WHEN 项目构建 THEN 系统 SHALL 能够通过 `mvn clean package` 成功编译打包
3. WHEN 项目启动 THEN 系统 SHALL 能够正常启动并提供健康检查端点 `/actuator/health`
4. WHEN 开发者查看项目 THEN 系统 SHALL 包含统一的代码格式化配置、.gitignore、README 文档
5. WHEN 项目运行 THEN 系统 SHALL 集成以下基础组件：
   - Spring Boot 3.x（Web、Validation、AOP）
   - MyBatis-Plus 3.x（通用 CRUD 和分页插件）
   - Sa-Token（认证授权框架，JWT 模式）
   - SLF4J + Logback（日志框架）
   - EasyExcel（Excel 读写库）
   - Lombok（编译期注解处理器）
   - MapStruct（编译期对象映射）
6. WHEN 项目配置 THEN 系统 SHALL 使用 `application.yml` + `application-dev.yml` + `application-prod.yml` 进行多环境配置管理

### 需求 2：PC 端前端项目基础架构搭建

**用户故事：** 作为一名前端开发者，我希望有一个基于 Vue 3 的现代化前端项目骨架，包含统一的设计规范和基础组件，以便能够高效地进行页面和组件的开发。

#### 验收标准

1. WHEN 项目初始化 THEN 系统 SHALL 基于 Vite + Vue 3 创建前端项目，包含以下目录结构：
   - `src/api`：API 接口封装
   - `src/assets`：静态资源（图片、样式）
   - `src/components`：公共组件
   - `src/composables`：组合式函数（Composition API hooks）
   - `src/layouts`：页面布局组件
   - `src/router`：Vue Router 路由配置
   - `src/stores`：Pinia 状态管理
   - `src/styles`：全局样式、CSS 变量、主题配置
   - `src/utils`：工具函数
   - `src/views`：页面视图组件
2. WHEN 项目构建 THEN 系统 SHALL 能够通过 `npm run build` 成功构建为静态资源
3. WHEN 项目启动开发模式 THEN 系统 SHALL 能够通过 `npm run dev` 启动 Vite 开发服务器，支持热更新
4. WHEN 项目运行 THEN 系统 SHALL 集成以下基础组件：
   - Vue 3（Composition API）
   - Element Plus（UI 组件库，按需引入）
   - ECharts（图表可视化）
   - Vue Router（路由管理）
   - Pinia（状态管理）
   - Axios（HTTP 请求，统一封装请求/响应拦截器）
5. WHEN 前端发起 API 请求 THEN 系统 SHALL 通过 Axios 拦截器自动附加 Sa-Token 认证信息，并统一处理错误响应
6. WHEN 项目初始化 THEN 系统 SHALL 建立全局设计规范：
   - 定义 CSS 变量体系（主色调、辅助色、文字色、边框色、间距系统、圆角等）
   - 统一 Element Plus 主题色配置
   - 定义全局排版规范（标题层级、正文字号、行高）
   - 封装通用样式工具类（间距、对齐、文本截断等）
7. WHEN 开发者创建新页面 THEN 系统 SHALL 提供以下可复用的基础组件：
   - `SearchForm`：通用搜索表单组件（支持条件折叠/展开、回车搜索、重置）
   - `DataTable`：通用数据表格组件（封装分页、排序、列配置）
   - `FormDialog`：通用表单弹窗组件（封装新增/编辑弹窗的通用逻辑）
   - `PageHeader`：页面标题栏组件（标题 + 操作按钮区）

### 需求 3：统一响应格式与全局异常处理

**用户故事：** 作为一名前端开发者，我希望后端 API 返回统一格式的响应数据和错误信息，以便前端能够统一处理请求结果。

#### 验收标准

**后端：**

1. WHEN 任何 API 请求成功 THEN 系统 SHALL 返回统一的 JSON 响应格式：`{ "code": 200, "message": "success", "data": {...} }`
2. WHEN 任何 API 请求发生业务异常 THEN 系统 SHALL 返回统一的错误格式：`{ "code": <错误码>, "message": "<错误描述>", "data": null }`
3. WHEN 请求参数校验失败 THEN 系统 SHALL 返回 400 状态码和具体的字段校验错误信息
4. WHEN 发生未捕获的系统异常 THEN 系统 SHALL 返回 500 状态码，记录详细错误日志，但不向前端暴露堆栈信息
5. WHEN 访问不存在的资源 THEN 系统 SHALL 返回 404 状态码和友好的错误提示

**PC 端前端：**

6. WHEN 前端收到错误响应 THEN 前端 SHALL 通过 Axios 响应拦截器统一弹出 Element Plus 消息提示
7. WHEN 前端收到 401 响应 THEN 前端 SHALL 清除本地 Token 并跳转至登录页
8. WHEN 前端收到 403 响应 THEN 前端 SHALL 展示"无权限访问"提示

## 阶段二：认证与基础管理

> **目标**：实现用户认证授权体系、用户管理、医疗机构管理、PC 端页面框架等基础管理功能，为后续业务模块提供完整的权限和元数据支撑。
> **前置依赖**：阶段一（基础设施搭建）

### 需求 4：用户认证与权限管理

**用户故事：** 作为一名系统管理员，我希望系统提供安全的多角色认证和细粒度的权限控制，支持按医院隔离的分级管理体系，以便不同角色的用户只能访问其授权范围内的功能和数据，同时让各医院管理员能够自主管理本院的注册用户。

#### 4.1 角色体系设计

系统采用**四级角色体系**，按权限从高到低排列：

| 角色 | 角色标识 | 数据范围 | 说明 |
|------|---------|---------|------|
| 超级管理员 | `super_admin` | 全局 | 平台级管理员，可管理所有医院、所有用户、所有数据 |
| 医院管理员 | `hospital_admin` | 本院 | 医院级管理员，可管理本院用户、查看本院所有病例数据 |
| 普通医生 | `doctor` | 本人 | 普通医生，可管理自己创建的病例和随访数据 |
| 家长 | `parent` | 本人 | 小程序家长端用户，可管理自己的宝宝和评测数据 |

#### 4.2 登录认证

**验收标准：**

**后端：**

1. WHEN 用户请求登录 THEN 系统 SHALL 验证用户名和密码（密码使用 BCrypt 加密存储），验证成功后通过 Sa-Token 生成 Token 并返回
2. WHEN 用户携带有效 Token 访问受保护的 API THEN 系统 SHALL 通过 Sa-Token 验证身份并允许访问
3. WHEN Token 过期 THEN 系统 SHALL 返回 401 状态码
4. WHEN 用户访问无权限的 API THEN 系统 SHALL 返回 403 状态码
5. WHEN 用户超过 6 个月未修改密码 THEN 系统 SHALL 在登录响应中标记需要修改密码
6. WHEN 用户首次使用默认密码登录 THEN 系统 SHALL 在登录响应中标记需要强制修改密码
7. WHEN 用户设置新密码 THEN 系统 SHALL 校验密码复杂度：长度 6-30 位，且必须同时包含数字和字母
8. WHEN 用户修改密码成功 THEN 系统 SHALL 使当前 Token 失效，强制用户重新登录
9. WHEN 用户登录/登出 THEN 系统 SHALL 记录登录日志（IP、时间、用户角色、所属医院）
10. WHEN 对外暴露用户 ID THEN 系统 SHALL 使用 Hashids 编码，不直接暴露数据库自增 ID
11. WHEN 登录成功 THEN 系统 SHALL 在 Token 中携带用户角色和所属医院信息，供后续权限校验使用

**PC 端前端：**

12. WHEN 前端登录成功 THEN 前端 SHALL 将 Token 存储到 Pinia 状态管理中，并持久化到 localStorage
13. WHEN 前端检测到 401 响应 THEN 前端 SHALL 清除本地 Token 并跳转至登录页
14. WHEN 用户访问登录页 THEN 前端 SHALL 展示现代化登录页面，包含：
    - 左侧品牌展示区（系统名称 + 简介 + 背景图）
    - 右侧登录表单（用户名 + 密码 + 登录按钮）
    - 「记住用户名」复选框（勾选后下次登录自动填充用户名，存储到 localStorage）
    - 「忘记密码?」链接（点击后弹出提示「请联系系统管理员重置密码」）
    - 支持回车键提交、表单校验、登录中 loading 状态
15. WHEN 登录响应标记需要强制修改密码 THEN 前端 SHALL 弹出密码修改对话框，用户必须修改密码后才能进入系统
16. WHEN 登录响应标记需要提醒修改密码（超过 6 个月） THEN 前端 SHALL 弹出温馨提示，建议用户前往个人中心修改密码，支持「立即修改」和「稍后再说」两个选项

#### 4.3 角色权限控制

**验收标准：**

**后端：**

1. IF 用户角色为超级管理员 THEN 系统 SHALL 允许访问所有功能，包括：
   - 管理所有医疗机构（单位）
   - 管理所有用户（跨医院），包括创建/编辑/禁用医院管理员
   - 查看和管理所有医院的病例数据、随访记录、统计分析
   - 系统配置、操作日志查看
2. IF 用户角色为医院管理员 THEN 系统 SHALL 允许访问以下功能：
   - 管理**本院用户**：查看本院用户列表，创建/编辑/禁用本院的普通医生账号
   - 查看**本院所有病例数据**：可查看本院所有医生创建的病例和随访记录
   - 病例管理：创建和管理自己的病例数据
   - 随访管理、影像查看、统计分析（数据范围限定为本院）
   - **不可**管理其他医院的用户和数据
   - **不可**创建或编辑医院管理员角色（仅超级管理员可操作）
3. IF 用户角色为普通医生 THEN 系统 SHALL 允许访问以下功能：
   - 病例管理：创建和管理**自己创建的**病例数据
   - 随访管理：创建和管理自己负责的随访记录
   - 影像查看：查看自己病例关联的影像文件
   - 统计分析：查看自己的数据统计
   - **不可**查看其他医生的病例数据（除非被授权共享）
   - **不可**管理用户账号
4. IF 用户角色为家长 THEN 系统 SHALL 仅允许通过小程序端访问家长相关功能（宝宝管理、身高评测等）
5. WHEN 任何 API 请求涉及数据查询 THEN 系统 SHALL 根据用户角色自动过滤数据范围：
   - 超级管理员：返回全局数据
   - 医院管理员：返回本院数据（按 `hospital_id` 过滤）
   - 普通医生：返回本人数据（按 `creator_id` 过滤）

### 需求 5：用户管理

**用户故事：** 作为一名系统管理员或医院管理员，我希望有一个专门的用户管理模块，能够方便地维护系统中的用户账号信息，包括创建、编辑、启用/禁用用户，以及管理个人资料，以便高效地管理系统的使用者。

> **说明**：用户管理是系统的核心基础元数据模块之一。超级管理员可管理所有用户（跨医院），医院管理员仅可管理本院用户。该模块与需求 4 的角色权限控制紧密配合，确保分级管理的安全性。

#### 5.1 用户数据模型

**验收标准：**

**后端：**

1. WHEN 系统管理用户数据 THEN 系统 SHALL 维护以下用户信息字段：
   - 基本信息：用户名（登录账号，唯一）、密码（BCrypt 加密）、真实姓名、性别、手机号、邮箱
   - 职业信息：所属医院（`hospital_id`，关联医疗机构表）、科室、职称、工号
   - 角色信息：角色标识（`super_admin` / `hospital_admin` / `doctor` / `parent`）
   - 状态信息：账号状态（启用/禁用）、最后登录时间、密码修改时间
   - 微信绑定：微信 OpenID（用于小程序登录绑定）
   - 审计字段：创建时间、更新时间、创建人
2. WHEN 系统对外暴露用户 ID THEN 系统 SHALL 使用 Hashids 编码，不直接暴露数据库自增 ID
3. WHEN 用户被创建时 THEN 系统 SHALL 校验用户名唯一性，医生角色必须关联一个医疗机构（`hospital_id`），家长角色除外

#### 5.2 用户列表与查询（分级管理）

**验收标准：**

**后端：**

1. WHEN 超级管理员请求用户列表 THEN 系统 SHALL 返回所有用户，支持按医院、角色、状态、关键词（用户名/姓名）筛选，支持分页和排序
2. WHEN 医院管理员请求用户列表 THEN 系统 SHALL 仅返回本院用户列表，自动按 `hospital_id` 过滤，支持按状态、关键词筛选
3. WHEN 普通医生请求用户列表 THEN 系统 SHALL 返回 403 状态码，拒绝访问
4. WHEN 请求用户详情 THEN 系统 SHALL 返回用户完整信息（密码字段除外），包含所属医院名称

**PC 端前端：**

5. WHEN 超级管理员访问用户管理页 THEN 前端 SHALL 提供用户列表页面，包含：
    - **页面标题栏**：标题「用户管理」 + 右侧「新增用户」按钮
    - **搜索区**：采用通用 `SearchForm` 组件
      - 第一行（常驻显示）：关键词输入框（用户名/姓名模糊搜索）、角色下拉选择、所属医院下拉选择、搜索按钮、重置按钮
      - 第二行（折叠区）：账号状态下拉、创建时间范围
    - **数据表格**：采用通用 `DataTable` 组件，列包含：用户名、真实姓名、角色（标签样式区分）、所属医院、科室、职称、状态（启用/禁用标签）、最后登录时间、操作列
    - **操作列**：编辑、重置密码、启用/禁用切换、删除
    - **批量操作**：支持批量启用/禁用
6. WHEN 医院管理员访问用户管理页 THEN 前端 SHALL 提供本院用户列表页面，包含：
    - **页面标题栏**：标题「用户管理」 + 副标题显示当前医院名称 + 右侧「新增用户」按钮
    - **搜索区**：关键词输入框、账号状态下拉（无需医院筛选，已自动限定本院）
    - **数据表格**：列包含：用户名、真实姓名、科室、职称、状态、最后登录时间、操作列
    - **操作列**：编辑、重置密码、启用/禁用切换（无删除权限）
7. WHEN 普通医生访问系统 THEN 前端 SHALL 隐藏用户管理菜单入口

#### 5.3 用户新增与编辑

**验收标准：**

**后端：**

1. WHEN 超级管理员创建用户 THEN 系统 SHALL 支持设置用户的角色（可选超级管理员/医院管理员/普通医生）、所属医院、科室、职称等全部信息
2. WHEN 医院管理员创建用户 THEN 系统 SHALL 仅允许创建角色为「普通医生」的用户，且所属医院自动设置为本院，不可修改
3. WHEN 超级管理员编辑用户 THEN 系统 SHALL 支持修改用户的所有信息，包括角色和所属医院
4. WHEN 医院管理员编辑用户 THEN 系统 SHALL 仅允许编辑本院的普通医生信息，**不可**修改用户角色为医院管理员或超级管理员，**不可**修改所属医院
5. WHEN 医院管理员尝试操作非本院用户 THEN 系统 SHALL 返回 403 状态码并拒绝操作
6. WHEN 创建用户时未指定密码 THEN 系统 SHALL 生成默认密码并在响应中返回（仅创建时返回一次）
7. WHEN 用户名已存在 THEN 系统 SHALL 返回明确的错误提示「用户名已存在」

**PC 端前端：**

8. WHEN 超级管理员点击「新增用户」 THEN 前端 SHALL 弹出抽屉（Drawer）表单，包含：
    - 基本信息区：用户名（必填）、真实姓名（必填）、性别（下拉）、手机号、邮箱
    - 职业信息区：所属医院（必填，下拉选择，支持搜索）、科室（选填）、职称（选填）、工号（选填）
    - 权限信息区：角色（必填，下拉选择：超级管理员/医院管理员/普通医生）
    - 初始密码区：自动生成或手动输入，支持复制
    - 底部操作栏：保存按钮 + 取消按钮
9. WHEN 医院管理员点击「新增用户」 THEN 前端 SHALL 弹出抽屉（Drawer）表单，包含：
    - 基本信息区：用户名（必填）、真实姓名（必填）、性别（下拉）、手机号、邮箱
    - 职业信息区：所属医院（只读，自动填充为本院）、科室（选填）、职称（选填）、工号（选填）
    - 权限信息区：角色（只读，固定显示「普通医生」）
    - 初始密码区：自动生成或手动输入，支持复制
10. WHEN 管理员点击编辑用户 THEN 前端 SHALL 弹出抽屉（Drawer）表单，自动回填用户现有信息，密码字段不显示
11. WHEN 表单提交 THEN 前端 SHALL 进行完整的表单校验（用户名必填、手机号格式、邮箱格式等），校验通过后提交保存

#### 5.4 用户状态管理

**验收标准：**

**后端：**

1. WHEN 管理员启用/禁用用户账号 THEN 系统 SHALL 立即生效，被禁用的用户当前 Token 失效且无法重新登录
2. WHEN 管理员重置用户密码 THEN 系统 SHALL 生成新的随机密码并返回，同时使该用户当前 Token 失效
3. WHEN 管理员删除用户 THEN 系统 SHALL 执行逻辑删除（设置删除标志），不物理删除数据
4. WHEN 删除的用户有关联的病例数据 THEN 系统 SHALL 保留病例数据不受影响，仅标记用户为已删除

**PC 端前端：**

5. WHEN 管理员点击启用/禁用按钮 THEN 前端 SHALL 弹出确认对话框（显示用户名和操作类型），确认后执行操作并刷新列表
6. WHEN 管理员点击重置密码 THEN 前端 SHALL 弹出确认对话框，确认后执行重置并弹窗显示新密码（支持一键复制）
7. WHEN 管理员点击删除用户 THEN 前端 SHALL 弹出二次确认对话框（红色警告样式），确认后执行删除

#### 5.5 个人中心

**验收标准：**

**后端：**

1. WHEN 用户查询个人信息 THEN 系统 SHALL 返回当前登录用户的完整个人信息（密码除外）
2. WHEN 用户更新个人信息 THEN 系统 SHALL 允许修改姓名、性别、手机号、邮箱等个人信息，**不可**修改用户名、角色、所属医院
3. WHEN 用户修改密码 THEN 系统 SHALL 验证旧密码正确后才允许设置新密码，新密码使用 BCrypt 加密存储

**PC 端前端：**

4. WHEN 用户访问个人中心页 THEN 前端 SHALL 展示个人信息页面，包含：
    - **个人信息卡片**：头像区域 + 基本信息展示（姓名、角色标签、所属医院、科室）
    - **信息编辑表单**：分为两个区域
      - 基本信息区：真实姓名、性别、手机号、邮箱（可编辑）；用户名、所属医院、角色（只读灰色展示）
      - 职业信息区：科室、职称、工号（可编辑）
    - **保存按钮**：底部固定保存按钮
5. WHEN 用户点击「修改密码」 THEN 前端 SHALL 弹出密码修改对话框，包含：旧密码、新密码、确认新密码三个输入框，支持密码强度提示
6. WHEN 密码修改成功 THEN 前端 SHALL 提示「密码修改成功，请重新登录」并自动跳转至登录页

### 需求 6：医疗机构（单位）管理

**用户故事：** 作为一名超级管理员，我希望有一个专门的医疗机构管理模块，能够全面维护系统中的医院和医疗机构信息，包括机构的基本信息、联系方式、状态管理等，以便为用户管理和数据隔离提供准确的基础元数据支撑。

> **说明**：医疗机构（单位）是系统数据隔离的核心维度。每个医院管理员和普通医生都必须归属于一个医疗机构，系统根据用户所属机构自动过滤数据范围。该模块仅超级管理员可访问。

#### 6.1 机构数据模型

**验收标准：**

**后端：**

1. WHEN 系统管理机构数据 THEN 系统 SHALL 维护以下机构信息字段：
   - 基本信息：机构名称（唯一）、机构简称、机构编码（唯一，用于系统内部标识）
   - 联系信息：联系人姓名、联系电话、联系地址、邮政编码
   - 扩展信息：机构级别（如三甲、三乙、二甲等）、机构类型（综合医院/专科医院/社区卫生服务中心等）、所在省市区
   - 状态信息：启用/禁用状态
   - 统计信息（只读）：关联用户数、关联病例数
   - 审计字段：创建时间、更新时间、创建人、备注
2. WHEN 系统对外暴露机构 ID THEN 系统 SHALL 使用 Hashids 编码，不直接暴露数据库自增 ID
3. WHEN 机构名称或编码已存在 THEN 系统 SHALL 返回明确的错误提示

#### 6.2 机构列表与查询

**验收标准：**

**后端：**

1. WHEN 超级管理员请求机构列表 THEN 系统 SHALL 返回分页的医疗机构列表，支持按名称、编码、状态、机构级别筛选，支持排序
2. WHEN 请求机构详情 THEN 系统 SHALL 返回机构完整信息，包含关联的用户数量和病例数量统计
3. WHEN 其他模块需要机构下拉选项 THEN 系统 SHALL 提供轻量级的机构选项列表接口（仅返回 ID + 名称），支持关键词搜索，仅返回启用状态的机构

**PC 端前端：**

4. WHEN 超级管理员访问单位管理页 THEN 前端 SHALL 提供机构列表页面，包含：
    - **页面标题栏**：标题「单位管理」 + 右侧「新增机构」按钮
    - **搜索区**：采用通用 `SearchForm` 组件
      - 第一行（常驻显示）：关键词输入框（名称/编码模糊搜索）、机构状态下拉、搜索按钮、重置按钮
      - 第二行（折叠区）：机构级别下拉、机构类型下拉
    - **数据表格**：采用通用 `DataTable` 组件，列包含：机构名称、机构编码、机构级别、联系人、联系电话、关联用户数、状态（启用/禁用标签）、操作列
    - **操作列**：查看详情、编辑、启用/禁用切换、删除
5. WHEN 管理员点击机构名称或「查看详情」 THEN 前端 SHALL 弹出详情抽屉（Drawer），展示机构完整信息和关联统计数据

#### 6.3 机构新增与编辑

**验收标准：**

**后端：**

1. WHEN 超级管理员新增机构 THEN 系统 SHALL 创建医疗机构记录，校验名称和编码的唯一性
2. WHEN 超级管理员编辑机构 THEN 系统 SHALL 更新医疗机构信息，校验名称和编码的唯一性（排除自身）
3. WHEN 机构信息变更 THEN 系统 SHALL 记录操作日志

**PC 端前端：**

4. WHEN 管理员点击「新增机构」 THEN 前端 SHALL 弹出抽屉（Drawer）表单，包含：
    - 基本信息区：机构名称（必填）、机构简称（选填）、机构编码（必填，支持自动生成）
    - 分类信息区：机构级别（下拉选择）、机构类型（下拉选择）、所在省市区（级联选择器）
    - 联系信息区：联系人姓名、联系电话、联系地址、邮政编码
    - 备注区：多行文本输入
    - 底部操作栏：保存按钮 + 取消按钮
5. WHEN 管理员点击编辑机构 THEN 前端 SHALL 弹出抽屉（Drawer）表单，自动回填机构现有信息
6. WHEN 表单提交 THEN 前端 SHALL 进行完整的表单校验（名称必填、编码必填且格式校验、电话格式等），校验通过后提交保存

#### 6.4 机构状态管理

**验收标准：**

**后端：**

1. WHEN 超级管理员启用/禁用机构 THEN 系统 SHALL 更新机构状态
2. WHEN 禁用机构 THEN 系统 SHALL 同时禁用该机构下所有用户账号，并使其 Token 失效
3. WHEN 启用机构 THEN 系统 SHALL 仅恢复机构状态，不自动恢复已禁用的用户账号（需管理员手动启用）
4. WHEN 超级管理员删除机构 THEN 系统 SHALL 检查是否有关联用户或病例数据：
   - 如有关联数据，则拒绝删除并返回明确提示（如「该机构下有 N 个用户和 M 条病例，无法删除」）
   - 如无关联数据，则执行逻辑删除

**PC 端前端：**

5. WHEN 管理员点击启用/禁用机构 THEN 前端 SHALL 弹出确认对话框：
   - 禁用时警告提示「禁用机构将同时禁用该机构下所有用户账号，是否继续？」
   - 启用时普通确认提示
6. WHEN 管理员点击删除机构 THEN 前端 SHALL 弹出二次确认对话框（红色警告样式），确认后执行删除
7. WHEN 删除被拒绝（有关联数据） THEN 前端 SHALL 展示详细的拒绝原因提示

#### 6.5 机构数据统计

**验收标准：**

**后端：**

1. WHEN 超级管理员查看机构统计 THEN 系统 SHALL 返回各机构的用户数量、病例数量、最近活跃时间等汇总数据

**PC 端前端：**

2. WHEN 管理员在机构列表页 THEN 前端 SHALL 在表格中直接展示各机构的关联用户数和病例数，点击数字可跳转到对应的用户列表或病例列表（自动带入机构筛选条件）

### 需求 7：PC 端前端布局与交互体验设计

**用户故事：** 作为一名医生/管理员，我希望系统有清晰的页面布局、高效的导航结构和流畅的交互体验，以便能够快速访问各个功能模块并高效完成日常工作。

#### 7.1 主布局框架

**验收标准：**

1. WHEN 用户登录成功 THEN 前端 SHALL 展示经典三栏布局：
   - **左侧边栏**：可折叠的导航菜单（宽度 210px，折叠后 64px），包含系统 Logo、菜单树
   - **顶部栏**：面包屑导航 + 右侧用户信息区（头像、用户名、下拉菜单：个人中心/修改密码/退出登录）
   - **主内容区**：页面内容渲染区域，带适当的内边距
2. WHEN 用户点击侧边栏折叠按钮 THEN 前端 SHALL 平滑动画切换侧边栏的展开/折叠状态，折叠后仅显示菜单图标
3. WHEN 页面切换 THEN 前端 SHALL 展示页面切换过渡动画（fade 或 slide），提升视觉流畅感

#### 7.2 导航菜单结构

**验收标准：**

1. WHEN 用户查看侧边栏菜单 THEN 前端 SHALL 按以下结构组织菜单（支持多级展开）：
   ```
   📊 工作台（首页/仪表盘）
   📋 病例管理
      ├── 性发育异常 (DSD)
      ├── 遗传性骨病 (FSS)
      ├── 中枢性性早熟 (CPP)
      ├── McCune-Albright (MAS)
      ├── 小于胎龄儿 (SGA)
      ├── 家族性矮小 (SSS)
      └── E路童萌 (ELTM)
   🏫 健康筛查
   📈 统计分析
   🔔 通知公告
   👥 用户管理（医院管理员：管理本院用户；超级管理员：管理所有用户）
   ⚙️ 系统管理（仅超级管理员可见）
      ├── 单位管理
      └── 操作日志
   ```
2. IF 用户角色不同 THEN 前端 SHALL 根据角色权限动态渲染菜单项，隐藏无权限的功能入口：
   - 超级管理员：显示所有菜单项
   - 医院管理员：显示工作台、病例管理、健康筛查、统计分析、通知公告、用户管理（本院），隐藏系统管理
   - 普通医生：显示工作台、病例管理、健康筛查、统计分析、通知公告，隐藏用户管理和系统管理
3. WHEN 用户点击菜单项 THEN 前端 SHALL 高亮当前选中的菜单项，并自动展开其父级菜单

#### 7.3 路由与页面导航

**验收标准：**

1. WHEN 用户点击左侧菜单 THEN 前端 SHALL 通过 Vue Router 切换到对应的功能页面，不刷新整个页面
2. WHEN 用户未登录直接访问受保护页面 THEN 前端 SHALL 通过路由守卫拦截并跳转至登录页，登录后自动跳回原页面
3. WHEN 用户访问不存在的路由 THEN 前端 SHALL 展示 404 页面
4. WHEN 页面路由变化 THEN 前端 SHALL 自动更新面包屑导航，展示当前页面的层级路径
5. WHEN 用户在浏览器中刷新页面 THEN 前端 SHALL 正确恢复当前路由和页面状态

#### 7.4 工作台首页

**验收标准：**

**后端：**

1. WHEN 用户请求工作台数据 THEN 系统 SHALL 返回病例总数、本月新增、随访待处理数等汇总数据

**PC 端前端：**

2. WHEN 用户登录后进入工作台 THEN 前端 SHALL 展示仪表盘页面，包含：
   - 数据概览卡片：病例总数、本月新增、随访待处理数等关键指标

   - 系统公告区域：展示最新的系统公告
3. WHEN 用户点击数据卡片 THEN 前端 SHALL 跳转到对应的详情列表页面

## 阶段三：核心业务 — 病例管理

> **目标**：实现系统最核心的患者病例管理功能，包括 7 种疾病类型的数据模型和 CRUD 操作，重点优化数据录入和检索查询效率。
> **前置依赖**：阶段二（认证与基础管理）

### 需求 8：患者病例管理（核心业务）

**用户故事：** 作为一名医生，我希望能够高效地管理患者病例数据，通过简洁的表单快速录入、通过灵活的搜索快速检索，以便对儿科内分泌疾病患者进行规范化的临床数据管理。

#### 8.1 病例列表与高效检索

**验收标准：**

**后端：**

1. WHEN 医生请求病例列表 THEN 系统 SHALL 返回分页的病例列表，支持按病例编号、性别、病历号、姓名、上传时间范围等多条件筛选
2. WHEN 医生查看患者详情 THEN 系统 SHALL 返回患者基本信息、疾病专项数据、随访记录列表和医学影像列表
3. WHEN 系统返回患者 ID THEN 系统 SHALL 使用 Hashids 编码，隐藏数据库主键

**PC 端前端：**

4. WHEN 医生进入某疾病类型的病例列表页 THEN 前端 SHALL 展示以下布局：
   - **页面标题栏**：疾病类型名称 + 右侧操作按钮组（新建病例、导出 Excel、批量下载）
   - **搜索区**：采用通用 `SearchForm` 组件，包含以下搜索条件：
     - 第一行（常驻显示）：病例编号、姓名、性别（下拉）、搜索按钮、重置按钮
     - 第二行（折叠区，点击"更多筛选"展开）：病历号、上传时间范围（日期选择器）
   - **数据表格**：使用通用 `DataTable` 组件，列配置根据疾病类型动态调整
5. WHEN 医生在搜索框中输入关键词并按回车 THEN 前端 SHALL 立即触发搜索请求
6. WHEN 医生点击"重置"按钮 THEN 前端 SHALL 清空所有搜索条件并重新加载默认列表
7. WHEN 医生点击表格行 THEN 前端 SHALL 高亮选中行，双击进入病例详情页
8. WHEN 医生点击操作列的"查看"图标 THEN 前端 SHALL 跳转到病例详情页（只读模式）
9. WHEN 医生点击操作列的"编辑"图标 THEN 前端 SHALL 跳转到病例编辑页
10. WHEN 医生点击操作列的"删除"图标 THEN 前端 SHALL 弹出确认对话框，确认后执行逻辑删除

#### 8.2 患者主表数据模型

**验收标准：**

**后端：**

1. WHEN 系统管理患者数据 THEN 系统 SHALL 维护患者主表 `Patient` Entity，包含以下字段分组：
   - **基本信息**：姓名、性别、出生日期、身份证号、联系电话
   - **编号体系**：病例编号（`case_num`，系统自动生成）、病历号（`medrec_num`，医院病历号）、患者编号（`user_num`）
   - **疾病分类**：疾病类型编码（`dis_class`，关联具体疾病子表）
   - **生长数据**：身高、体重、BMI、骨龄（R 型/C 型）
   - **家庭信息**：父亲身高/体重、母亲身高/体重、母亲初潮年龄、家族史
   - **出生信息**：胎龄周、出生体重/身长、分娩方式、窒息抢救史
   - **就诊信息**：初诊时间、确诊年龄、主诉、ICD 编码
   - **小程序关联**：小程序身份标识（`xcx_card`）、期望身高、当前城市
   - **管理字段**：导入人员（`creator_id`）、上传机构（`hospital_id`）、删除标志、创建时间、修改时间
2. WHEN 系统自动生成病例编号 THEN 系统 SHALL 按照规则生成唯一的病例编号（格式：疾病类型前缀 + 年月 + 序号，如 `DSD202604001`），确保编号不重复
3. WHEN 病例创建后 THEN 系统 SHALL 不允许修改疾病类型（`dis_class`），疾病类型在创建时确定且不可变更
4. WHEN 同一患者需要记录多种疾病 THEN 系统 SHALL 为每种疾病类型创建独立的病例记录，通过病历号（`medrec_num`）关联同一患者的不同疾病病例

#### 8.3 病例录入与编辑（简化输入）

**验收标准：**

**后端：**

1. WHEN 医生新建病例 THEN 系统 SHALL 创建患者主表记录，自动生成病例编号，并根据疾病类型创建对应的疾病子表记录
2. WHEN 医生编辑病例 THEN 系统 SHALL 更新患者基本信息和疾病专项数据，并记录修改日志
3. WHEN 医生删除病例 THEN 系统 SHALL 执行逻辑删除（设置删除标志），不物理删除数据

**PC 端前端：**

4. WHEN 医生新建/编辑病例 THEN 前端 SHALL 采用**分区表单**布局，将表单字段按业务含义分组：
   - 使用 Element Plus 的 `el-card` 或折叠面板（`el-collapse`）将表单分为多个区域
   - 每个区域有清晰的标题（如"基本信息"、"体格检查"、"实验室检查"、"影像检查"、"诊疗方案"等）
   - 区域可独立折叠/展开，方便医生聚焦当前填写的部分
5. WHEN 医生填写表单 THEN 前端 SHALL 提供以下输入优化：
   - **智能默认值**：性别默认不选、日期默认当天、数值字段显示单位提示（如 cm、kg）
   - **输入联动**：填写出生日期后自动计算年龄；填写身高体重后自动计算 BMI
   - **输入校验**：实时校验（失焦时校验），数值范围提示（如身高 30-250cm）
   - **快捷输入**：常用诊断支持下拉选择 + 手动输入混合模式
6. WHEN 医生提交表单 THEN 前端 SHALL 进行完整的表单校验，未通过时自动滚动到第一个错误字段并高亮提示
7. WHEN 医生编辑已有病例 THEN 前端 SHALL 自动回填所有已有数据，并标记哪些字段被修改过
8. WHEN 表单页面有未保存的修改且用户尝试离开 THEN 前端 SHALL 弹出确认对话框提示用户保存

#### 8.4 七种疾病类型数据模型

**验收标准：**

**后端：**

1. WHEN 系统处理疾病类型 THEN 系统 SHALL 支持以下 7 大疾病类型及其独立数据模型：
   - 10000001：性发育异常 (DSD) — 独立 Entity `DsdCase`、Mapper、Service
   - 10000002：遗传性骨病 (FSS) — 独立 Entity `FssCase`、Mapper、Service
   - 10000003：中枢性性早熟 (CPP) — 独立 Entity `CppCase`、Mapper、Service
   - 10000004：McCune-Albright (MAS) — 独立 Entity `MasCase`、Mapper、Service
   - 10000005：小于胎龄儿 (SGA) — 独立 Entity `SgaCase`、Mapper、Service
   - 10000006：家族性矮小 (SSS) — 独立 Entity `SssCase`、Mapper、Service
   - 10000007：E路童萌 (ELTM) — 独立 Entity `EltmCase`、Mapper、Service

**PC 端前端：**

2. WHEN 医生新建/编辑病例 THEN 前端 SHALL 根据疾病类型动态加载对应的表单组件（`DsdForm.vue`、`FssForm.vue` 等），每个表单组件内部按业务分区拆分为多个子组件
3. WHEN 开发者维护疾病表单 THEN 每个疾病表单组件 SHALL 拆分为独立的子组件文件（如 `DsdBasicInfo.vue`、`DsdPhysicalExam.vue`、`DsdLabTest.vue` 等），单个组件文件不超过 500 行

#### 8.5 数据导出与批量操作

**验收标准：**

**后端：**

1. WHEN 医生请求导出 Excel THEN 系统 SHALL 使用 EasyExcel 根据当前筛选条件导出病例数据为 Excel 文件
2. WHEN 医生请求批量下载 THEN 系统 SHALL 将选中病例的相关文件打包为 ZIP 下载
3. WHEN 医生请求 SDS 计算 THEN 系统 SHALL 根据身高、年龄、性别计算标准差分数（SDS）

**PC 端前端：**

4. WHEN 医生点击"导出 Excel"按钮 THEN 前端 SHALL 显示导出进度提示，导出完成后自动触发浏览器下载
5. WHEN 医生勾选多条病例后点击"批量下载" THEN 前端 SHALL 显示下载进度，未勾选时按钮置灰并提示"请先选择病例"

## 阶段四：核心业务 — 随访与影像

> **目标**：实现患者随访跟踪和医学影像管理功能，完善核心临床数据管理闭环。
> **前置依赖**：阶段三（病例管理）

### 需求 9：随访管理

**用户故事：** 作为一名医生，我希望能够为患者创建和管理随访记录，通过清晰的时间线视图跟踪患者的生长发育情况和治疗效果。

#### 9.1 通用随访数据模型

**验收标准：**

**后端：**

1. WHEN 系统管理随访数据 THEN 系统 SHALL 维护通用随访模型 `PatientFollowUp` Entity，包含以下字段分组：
   - **基础测量**：身高（Ht）、体重（Wt）、BMI、体脂率、腰围、臀围
   - **骨龄评估**：R 系列骨龄（R-TW3、R-GP 等）、C 系列骨龄
   - **发育分期**：生殖器分期、阴毛分期、乳房分期
   - **生长因子**：IGF-1、IGFBP-3
   - **甲状腺功能**：T3、T4、FT3、FT4、TSH
   - **血糖/胰岛素**：空腹血糖、空腹胰岛素、糖化血红蛋白
   - **性激素**：LH、FSH、E2、T、DHT、SHBG
   - **肝肾功能**：ALT、AST、BUN、Cr 等
   - **影像检查**：性腺 B 超、骨密度
   - **诊疗方案**：用药记录（药物名称、剂量、频次）、剂量调整
   - **其他**：是否达终身高、随访日期、备注
   - **管理字段**：关联患者 ID、创建人、创建时间、修改时间、删除标志
2. IF 疾病类型为 MAS THEN 系统 SHALL 使用 MAS 专用随访模型 `MasFollowUp`，在通用字段基础上额外包含：
   - **皮肤检查**：咖啡斑分布、大小、变化情况
   - **骨骼检查**：骨纤维异常增殖部位、骨折史
   - **多器官 B 超**：子宫 B 超、卵巢 B 超、甲状腺 B 超、肾上腺 B 超
   - **影像学**：头颅 CT/MR、全身骨扫描
   - **骨代谢检查**：血钙、血磷、ALP、25-OH-VD、PTH
   - **内分泌激素全套**：GH、PRL、ACTH、皮质醇等

#### 9.2 随访 CRUD 操作

**验收标准：**

**后端：**

1. WHEN 医生请求某患者的随访列表 THEN 系统 SHALL 返回该患者的所有随访记录，按时间倒序排列
2. WHEN 医生新增随访记录 THEN 系统 SHALL 创建随访记录，根据疾病类型选择通用随访模型或 MAS 专用随访模型
3. WHEN 医生编辑随访记录 THEN 系统 SHALL 更新随访数据并记录修改日志
4. WHEN 医生删除随访记录 THEN 系统 SHALL 执行逻辑删除

**PC 端前端：**

6. WHEN 医生查看患者的随访记录 THEN 前端 SHALL 在病例详情页中以**时间线列表**形式展示所有随访记录，每条记录显示随访日期、关键指标摘要（身高/体重/BMI）和操作按钮
7. WHEN 医生新增/编辑随访记录 THEN 前端 SHALL 采用与病例表单一致的**分区表单**布局，按业务分组（基础测量、骨龄评估、实验室检查等）
8. WHEN 医生填写随访表单 THEN 前端 SHALL 自动带入上次随访的部分数据作为参考（灰色显示），方便医生对比填写
9. IF 疾病类型为 MAS THEN 前端 SHALL 加载 MAS 专用随访表单组件，包含额外的专项检查区域

### 需求 10：医学影像处理

**用户故事：** 作为一名医生，我希望能够上传和管理患者的医学影像文件（如骨龄 X 光片），以便在系统中查看和分析影像数据。

#### 验收标准

**后端：**

1. WHEN 医生上传影像文件 THEN 系统 SHALL 接收并存储 DICOM 格式的医学影像文件，返回文件访问路径
2. WHEN 医生请求查看影像 THEN 系统 SHALL 提供影像文件的下载/流式访问接口
3. WHEN 医生上传通用文件 THEN 系统 SHALL 支持通用文件的上传和下载
4. WHEN 文件上传 THEN 系统 SHALL 校验文件大小和格式，拒绝不合规的文件
5. WHEN 系统存储文件 THEN 系统 SHALL 按日期和患者 ID 组织文件目录结构，便于管理和备份

**PC 端前端：**

6. WHEN 医生查看影像 THEN 前端 SHALL 在病例详情页中提供影像文件区域，包含：
   - 影像缩略图网格展示
   - 上传按钮支持拖拽上传和点击上传
   - 上传进度条展示
7. WHEN 医生点击 DICOM 影像缩略图 THEN 前端 SHALL 打开专业的 DICOM 影像查看器，支持：
   - 基础操作：缩放、旋转、平移、翻转
   - 窗宽窗位调节：支持预设窗口（骨窗、软组织窗等）和手动拖拽调节
   - 测量标注：支持长度测量、角度测量、ROI 标注
   - 影像信息：显示 DICOM 元数据（患者信息、检查信息、设备信息等）
   - 技术方案：使用 Cornerstone.js 3.x（cornerstone3D）或同等开源 DICOM 渲染库实现
8. WHEN 医生点击非 DICOM 格式的普通图片 THEN 前端 SHALL 弹出大图预览（支持缩放、旋转）
9. WHEN 医生上传文件 THEN 前端 SHALL 在上传前校验文件格式和大小，不合规时给出明确提示

**用户故事：** 作为一名医生/研究人员，我希望能够管理学校儿童健康筛查数据，包括学生基本信息和多种标准化评估问卷，以便进行儿童健康评估和研究。

7. WHEN 用户点击「批量导入」 THEN 前端 SHALL 弹出导入对话框，支持：
   - 下载 Excel 导入模板
   - 上传 Excel 文件（拖拽或点击上传）
   - 展示导入结果（成功数、失败数、失败明细）
8. WHEN 用户查看学生详情 THEN 前端 SHALL 采用**标签页（Tabs）**布局展示 7 张问卷：
   - 每张问卷一个标签页，标签页标题显示问卷名称和填写状态（已填/未填）
   - 问卷表单采用分组布局，每组维度一个区域
   - 支持单张问卷独立保存
9. WHEN 用户填写问卷 THEN 前端 SHALL 提供批量选择控件（如 Likert 量表使用单选按钮组横向排列），减少点击次数

### 需求 12：微信小程序家长端

**用户故事：** 作为一名家长，我希望通过微信小程序便捷地录入儿童生长数据、查看身高评测结果并与医生端互通，以便随时随地参与孩子的健康管理。

#### 12.1 家长端小程序项目基础架构

**验收标准：**

1. WHEN 项目初始化 THEN 系统 SHALL 基于 uni-app (Vue 3) 创建微信小程序项目（`eksjk-miniapp/`），包含以下目录结构：
   - `src/api`：API 接口封装（基于 uni.request 统一封装）
   - `src/components`：公共组件
   - `src/pages`：页面文件
   - `src/stores`：Pinia 状态管理
   - `src/utils`：工具函数
   - `src/static`：静态资源
2. WHEN 项目构建 THEN 系统 SHALL 能够通过 HBuilderX 或 CLI 编译为微信小程序，并在微信开发者工具中正常预览
3. WHEN 小程序发起 API 请求 THEN 系统 SHALL 通过请求拦截器自动附加 Sa-Token 认证信息，统一处理错误响应
4. WHEN 小程序启动 THEN 系统 SHALL 展示简洁的品牌启动页（Logo + 系统名称），随后自动跳转至首页或登录页

#### 12.2 微信授权登录

**验收标准：**

**后端：**

1. WHEN 家长通过微信授权登录 THEN 系统 SHALL 调用微信 API 获取 OpenID，创建或关联用户记录，通过 Sa-Token 返回 Token
2. WHEN 家长首次登录 THEN 系统 SHALL 自动创建家长用户记录，角色为「家长」
3. WHEN Token 过期 THEN 系统 SHALL 返回 401 状态码，小程序端自动重新发起微信登录

**小程序前端：**

4. WHEN 家长打开小程序 THEN 前端 SHALL 检查本地 Token 是否有效，无效时自动调用 `wx.login` 获取 code 并发送至后端换取 Token
5. WHEN 首次登录需要手机号 THEN 前端 SHALL 展示微信手机号快捷登录按钮，一键授权获取手机号
6. WHEN 登录成功 THEN 前端 SHALL 将 Token 存储到本地缓存（`uni.setStorageSync`），后续请求自动携带

#### 12.3 家长个人信息管理

**验收标准：**

**后端：**

1. WHEN 家长保存/查询个人信息 THEN 系统 SHALL 支持联系人姓名、手机号、身份证、籍贯等信息的存取

**小程序前端：**

3. WHEN 家长点击编辑个人信息 THEN 前端 SHALL 展示表单页面，支持修改联系人姓名、手机号、身份证号、籍贯等信息
4. WHEN 家长提交个人信息 THEN 前端 SHALL 进行表单校验（手机号格式、身份证格式），校验通过后提交保存

#### 12.4 宝宝信息管理

**验收标准：**

**后端：**

1. WHEN 家长添加/编辑/删除宝宝信息 THEN 系统 SHALL 管理儿童的姓名、性别、出生日期、身高体重等数据
2. WHEN 家长查询宝宝列表 THEN 系统 SHALL 返回该家长名下所有儿童信息

**小程序前端：**

   - 姓名（必填）、性别（必填，男/女选择器）、出生日期（必填，日期选择器）
   - 当前身高（选填，数字输入 + cm 单位）、当前体重（选填，数字输入 + kg 单位）
   - 头像上传（选填，支持拍照或从相册选择）

**验收标准：**

**后端：**

1. WHEN 家长进行身高评测 THEN 系统 SHALL 根据身高、年龄、性别计算 SDS/百分位并返回评测结果

**小程序前端：**

   - 测量日期（默认当天，可修改）
   - 身高输入（数字键盘，单位 cm，保留一位小数）
   - 体重输入（数字键盘，单位 kg，保留一位小数）
   - 提交评测按钮
4. WHEN 评测提交成功 THEN 前端 SHALL 展示评测结果页面，包含：
   - SDS 值和百分位排名（以直观的图形化方式展示，如进度条或仪表盘）
   - 评测结论文字说明（如「身高处于同龄儿童中等水平」）
   - 与上次评测的对比（身高增长值、时间间隔）
5. WHEN 家长查看历史评测 THEN 前端 SHALL 以列表形式展示历次评测记录，每条记录显示日期、身高、体重、SDS 值
6. WHEN 家长查看生长曲线 THEN 前端 SHALL 使用 uCharts 绘制身高/体重生长曲线图，叠加 WHO 标准参考线（P3/P50/P97），直观展示生长趋势

#### 12.6 医生绑定与数据同步

**验收标准：**

**后端：**

1. WHEN 家长绑定医生 THEN 系统 SHALL 建立家长与医生的关联关系，一个家长同一时间只能绑定一个医生，支持解绑后重新绑定
2. WHEN 家长提交评测数据 THEN 系统 SHALL 将数据标记为「待同步」状态，完整的数据同步状态机为：
   - `pending`（待同步）→ `reviewing`（待审核，医生端可见）→ `approved`（已通过）/ `rejected`（已拒绝）
   - 审核通过后数据自动同步到医生端病例系统，状态变为 `synced`（已同步）
   - 审核拒绝时记录拒绝原因，家长端可查看拒绝原因并重新提交
3. WHEN 数据同步失败 THEN 系统 SHALL 将状态标记为 `sync_failed`（同步失败），记录失败原因，支持管理员手动重试
4. WHEN 家长查询评测数据 THEN 系统 SHALL 返回每条数据的当前同步状态，家长可了解数据处理进度

**小程序前端：**

5. WHEN 家长点击「绑定医生」 THEN 前端 SHALL 支持通过扫描医生二维码或输入医生邀请码进行绑定
6. WHEN 绑定成功 THEN 前端 SHALL 在「我的」页面展示已绑定的医生信息（姓名、科室、医院），支持解绑操作
7. WHEN 家长提交评测数据 THEN 前端 SHALL 提示「数据已提交，等待医生审核」，并在历史记录中显示当前同步状态标签（待审核/已通过/已拒绝/已同步）
8. WHEN 评测数据被拒绝 THEN 前端 SHALL 在历史记录中显示拒绝原因，并提供「重新提交」按钮

#### 12.7 家长端小程序底部导航与页面结构

**验收标准：**

1. WHEN 家长使用小程序 THEN 前端 SHALL 提供底部 TabBar 导航，包含以下页面：
   ```
   🏠 首页（宝宝列表 + 快捷操作）
   📏 评测（身高评测入口）
   📊 记录（历史评测记录 + 生长曲线）
   👤 我的（个人信息 + 医生绑定 + 设置）
   ```
2. WHEN 页面切换 THEN 前端 SHALL 保持流畅的切换体验，TabBar 当前选中项高亮显示
3. WHEN 小程序加载数据 THEN 前端 SHALL 展示 loading 骨架屏，避免白屏等待
4. WHEN 网络异常 THEN 前端 SHALL 展示友好的错误提示页面，提供「重试」按钮
5. WHEN 小程序启动时检测到新版本 THEN 前端 SHALL 通过 `wx.getUpdateManager` 提示用户更新，强制更新时自动重启小程序

#### 14.4 数据库兼容性设计与数据迁移

**用户故事：** 作为一名运维人员/开发者，我希望新系统的数据库表结构充分考虑与 V1 的兼容性，并提供可靠的数据导入脚本，支持多次增量导入，以便实现从 V1 到 V2 的平滑迁移，确保迁移过程中不丢失任何业务数据。

> **说明**：V1 系统基于 Django ORM，数据库包含 29 个数据模型，分布在 5 个模块中（login、datamain、school、xcx、notiopi）。V2 需要兼容现有表结构，同时为新增功能（如数据同步状态机、四级角色体系等）扩展必要的字段和表。数据导入脚本需要支持**多次增量导入**，即在 V1 系统继续运行的过渡期内，可以多次执行导入脚本将新增/变更的数据同步到 V2 系统。

##### 14.4.1 数据库表结构兼容性设计

**验收标准：**

1. WHEN V2 系统设计数据库表结构 THEN 系统 SHALL 以 V1 现有表结构为基础进行设计，确保以下核心表的字段兼容：
   - **用户模块**：`User`（用户表，V1 继承自 Django AbstractUser）、`Permission`（权限表）、`role`（角色表）、`log`（登录日志）、`Unit`（医疗机构）、`StandaUnit`（标准单位）、`PersUnit`（个人单位）
   - **病例模块**：`Patient`（患者主表）、`Case`/DSD、`Short`/FSS、`Sexprecocity`/CPP、`Mas`/MAS、`SGA`、`JzxShort`/SSS、`SzfyEltm`/ELTM（7 种疾病子表）
   - **随访模块**：`PatFoll`（通用随访）、`MasFoll`（MAS 专用随访）
   - **学校模块**：`Student`（学生主表）、`Cchkn`/SDQ、`Cbq`、`Mqzyfs`、`Qzhd`、`Pmbl`、`Sthd`、`Smxg`/CSHQ（7 张问卷子表）
   - **小程序模块**：`ChartUser`（微信用户）
   - **通知模块**：`Notice`（公告）、`PerNoticeLog`（公告阅读记录）、`Opinion`（意见反馈）
   - **日志模块**：`OperLog`（操作日志）
2. WHEN V2 系统设计 Java Entity THEN 系统 SHALL 保留 V1 所有现有字段的名称和类型映射，不修改已有字段名，仅在必要时新增字段
3. WHEN V2 需要新增字段 THEN 系统 SHALL 将新增字段设计为**可空（nullable）**或带**默认值**，确保不影响 V1 存量数据的兼容性。V2 新增的字段包括但不限于：
   - `User` 表新增：`role_code`（四级角色标识）、`password_changed_at`（密码修改时间）、`wx_openid`（微信 OpenID）
   - `Patient` 表新增：`sync_status`（数据同步状态）、`sync_time`（同步时间）
   - `ChartUser` 表新增：`sync_status`（同步状态机字段：pending/reviewing/approved/rejected/synced/sync_failed）、`reject_reason`（拒绝原因）
4. IF V2 需要新增数据库表 THEN 系统 SHALL 通过独立的 SQL 脚本创建，脚本纳入版本管理（`eksjk_v2/sql/` 目录），按版本号命名（如 `V2.0.0__init_schema.sql`、`V2.0.1__add_sync_status.sql`）
5. WHEN V2 系统连接数据库 THEN 系统 SHALL 兼容 MySQL 8.0+，MyBatis-Plus Entity 的 `@TableName` 注解映射到 V1 现有表名
6. WHEN 系统处理现有数据 THEN 系统 SHALL 保持与 V1 版本**完全相同的 Hashids 编码规则**（相同的 salt、minLength、alphabet 配置），确保 V1 生成的 Hashids 编码在 V2 中可正确解码

##### 14.4.2 数据导入脚本开发

**验收标准：**

1. WHEN 开发者执行数据导入 THEN 系统 SHALL 提供一套完整的 Java 数据导入工具（位于 `eksjk-web` 模块的 `migration` 包下），以 Spring Boot CommandLineRunner 或独立 Main 方法的形式运行
2. WHEN 数据导入脚本运行 THEN 系统 SHALL 按以下顺序依次导入各模块数据（确保外键依赖关系正确）：
   - **第 1 步**：基础数据 — 医疗机构（`Unit`）、角色权限（`role`、`Permission`）
   - **第 2 步**：用户数据 — 用户账号（`User`），V1 的 `level` 字段映射为 V2 的四级角色标识（`level=1` → `super_admin`，`level=0` → `doctor`）
   - **第 3 步**：病例数据 — 患者主表（`Patient`）+ 7 种疾病子表
   - **第 4 步**：随访数据 — 通用随访（`PatFoll`）+ MAS 专用随访（`MasFoll`）
   - **第 5 步**：学校数据 — 学生主表（`Student`）+ 7 张问卷子表
   - **第 6 步**：小程序数据 — 微信用户（`ChartUser`）
   - **第 7 步**：辅助数据 — 公告（`Notice`）、反馈（`Opinion`）、操作日志（`OperLog`）、登录日志（`log`）
3. WHEN 每个导入步骤执行 THEN 系统 SHALL 输出详细的导入日志，包含：导入表名、总记录数、成功数、跳过数（已存在）、失败数、失败原因、耗时

##### 14.4.3 增量导入支持

**验收标准：**

1. WHEN 数据导入脚本多次执行 THEN 系统 SHALL 支持**幂等性增量导入**，即多次运行同一脚本不会产生重复数据
2. WHEN 导入脚本检测到目标表中已存在相同主键的记录 THEN 系统 SHALL 根据配置策略执行以下操作之一：
   - **跳过模式**（默认）：跳过已存在的记录，仅导入新增记录
   - **更新模式**：比较源数据和目标数据的 `updated_at`（修改时间）字段，仅更新源数据更新时间晚于目标数据的记录
   - **强制覆盖模式**：无条件覆盖目标数据（需通过命令行参数 `--mode=force` 显式指定）
3. WHEN 增量导入执行 THEN 系统 SHALL 通过以下机制识别新增和变更数据：
   - 以数据库主键（`id`）作为唯一标识判断记录是否已存在
   - 以 `updated_at`（修改时间）字段判断记录是否有变更
   - 对于没有 `updated_at` 字段的表（如日志表），以主键判断是否已导入
4. WHEN 导入脚本运行 THEN 系统 SHALL 支持通过命令行参数控制导入行为：
   - `--step=1,2,3`：指定执行哪些步骤（支持单步或多步，默认全部）
   - `--mode=skip|update|force`：指定导入模式（默认 skip）
   - `--batch-size=500`：指定批量插入的批次大小（默认 500）
   - `--dry-run`：试运行模式，仅输出导入计划和统计信息，不实际写入数据
   - `--source-db`：指定 V1 源数据库连接信息（如果 V1 和 V2 使用不同的数据库实例）
5. WHEN 导入过程中发生错误 THEN 系统 SHALL 按表级别进行事务管理：单表导入失败时回滚该表的事务，不影响其他表的导入，并在最终报告中汇总所有失败信息

##### 14.4.4 数据校验与导入报告

**验收标准：**

1. WHEN 数据导入完成 THEN 系统 SHALL 生成导入报告（输出到控制台 + 写入日志文件），包含：
   - 导入开始/结束时间、总耗时
   - 每张表的导入统计：源数据总数、新增数、更新数、跳过数、失败数
   - 失败记录的详细信息（主键 ID、失败原因）
   - 数据一致性校验结果（源表和目标表的记录数对比）
2. WHEN 导入完成后 THEN 系统 SHALL 自动执行数据一致性校验：
   - 对比 V1 源表和 V2 目标表的记录总数
   - 抽样校验关键字段的数据一致性（如患者姓名、病例编号等）
   - 校验外键关联的完整性（如患者主表与疾病子表的关联是否完整）
3. IF 数据一致性校验发现差异 THEN 系统 SHALL 在报告中标记差异详情，并给出建议的修复操作
4. WHEN 导入脚本运行 THEN 系统 SHALL 在导入前自动备份提示（输出提醒信息：「建议在导入前备份目标数据库」），但不强制执行备份
