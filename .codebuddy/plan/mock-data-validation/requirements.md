# 需求文档：Mock 数据脚本

> **实施优先级：Plan 3**
> **前置依赖：Plan 1（K8S 部署迁移）完成，MySQL 已在 K8S 中运行**
> **后续依赖：Plan 4（测试验证）的集成测试和 E2E 测试需要 Mock 数据作为测试基础**

## 引言

EKSJK V2 系统进入测试验证阶段，需要在本地 K8S 环境中快速初始化一套完整的 Mock 数据，以便核对各业务模块的功能正确性。

Mock 数据脚本的核心目标：
1. 覆盖系统所有角色（超级管理员、医院管理员、普通医生、家长）
2. 覆盖系统全部 7 种疾病类型的患者和病例数据
3. 覆盖随访记录、生长数据等关联数据
4. 提供一键初始化和一键清理能力，方便反复验证

**关键约束：**
- Mock 数据以 SQL 脚本形式提供，直接导入 MySQL 数据库
- 所有密码统一使用 BCrypt 加密（明文 `Test@1234`）
- 患者姓名、身份证号等敏感字段使用明显的测试标识（如 `测试患者_001`），避免与真实数据混淆
- 脚本必须支持幂等执行（重复执行不报错，使用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`）

## 需求

### 需求 1：用户与权限 Mock 数据

**用户故事：** 作为一名开发者，我希望有覆盖所有角色的测试账号，以便验证 RBAC 权限模型的正确性。

#### 验收标准

1. WHEN 执行 Mock 数据脚本 THEN 系统 SHALL 创建以下测试账号：

   | 账号 | 密码 | 角色 | 所属医院 | 说明 |
   |------|------|------|----------|------|
   | `super_admin` | `Test@1234` | 超级管理员 | 无 | 可管理所有数据 |
   | `hospital_admin_1` | `Test@1234` | 医院管理员 | 测试医院A | 管理医院A用户和数据 |
   | `hospital_admin_2` | `Test@1234` | 医院管理员 | 测试医院B | 管理医院B用户和数据 |
   | `doctor_1` | `Test@1234` | 普通医生 | 测试医院A | 仅管理自己的病例 |
   | `doctor_2` | `Test@1234` | 普通医生 | 测试医院A | 仅管理自己的病例 |
   | `doctor_3` | `Test@1234` | 普通医生 | 测试医院B | 仅管理自己的病例 |
   | `parent_1` | `Test@1234` | 家长 | 无 | 小程序端访问 |

2. WHEN 使用 `super_admin` 登录 THEN 系统 SHALL 能查询到所有医院、所有医生、所有患者数据
3. WHEN 使用 `hospital_admin_1` 登录 THEN 系统 SHALL 只能查询到测试医院A的数据，无法看到医院B的数据
4. WHEN 使用 `doctor_1` 登录 THEN 系统 SHALL 只能查询到 `doctor_1` 自己创建的患者和病例数据
5. WHEN 使用 `parent_1` 登录 THEN 系统 SHALL 只能访问家长端相关接口，无法访问医生端接口

---

### 需求 2：医院 Mock 数据

**用户故事：** 作为一名开发者，我希望有多家测试医院数据，以便验证多租户数据隔离的正确性。

#### 验收标准

1. WHEN 执行 Mock 数据脚本 THEN 系统 SHALL 创建以下测试医院：

   | 医院名称 | 医院编码 | 说明 |
   |----------|----------|------|
   | 测试医院A | `HOSPITAL_A` | 有2名医生、多名患者 |
   | 测试医院B | `HOSPITAL_B` | 有1名医生、少量患者 |

2. WHEN 查询医院列表 THEN 系统 SHALL 返回上述2家医院的完整信息（名称、编码、创建时间）
3. IF 医院管理员查询患者列表 THEN 系统 SHALL 只返回本院患者，不跨院显示

---

### 需求 3：患者基础信息 Mock 数据

**用户故事：** 作为一名开发者，我希望有覆盖 7 种疾病类型的患者数据，以便验证患者管理模块的正确性。

#### 验收标准

1. WHEN 执行 Mock 数据脚本 THEN 系统 SHALL 为每种疾病类型各创建至少 3 名患者，共计 ≥ 21 名患者：

   | 疾病类型 | 疾病编码 | 患者数量 | 创建医生 |
   |----------|----------|----------|----------|
   | 性发育异常 (DSD) | 10000001 | 3名 | doctor_1 |
   | 遗传性骨病 (FSS) | 10000002 | 3名 | doctor_1 |
   | 中枢性性早熟 (CPP) | 10000003 | 3名 | doctor_2 |
   | McCune-Albright (MAS) | 10000004 | 3名 | doctor_2 |
   | 小于胎龄儿 (SGA) | 10000005 | 3名 | doctor_3 |
   | 家族性矮小 (SSS) | 10000006 | 3名 | doctor_3 |
   | E路童萌 (ELTM) | 10000007 | 3名 | doctor_1 |

2. WHEN 查询患者列表 THEN 系统 SHALL 每条患者记录包含以下字段：
   - 患者姓名（格式：`测试患者_DSD_001`，含疾病类型标识）
   - 性别（男/女各占约一半）
   - 出生日期（覆盖 2010～2020 年范围，模拟儿科患者年龄段）
   - 身份证号（格式：`110101YYYYMMDD001X`，使用测试号段）
   - 联系电话（格式：`138XXXX0001`，使用测试号段）
   - 疾病类型编码（`disClass`）
   - 所属医院 ID
   - 创建医生 ID

3. WHEN 按疾病类型筛选患者 THEN 系统 SHALL 返回对应疾病类型的患者列表，数量与 Mock 数据一致
4. WHEN 按医院筛选患者 THEN 系统 SHALL 只返回该医院的患者

---

### 需求 4：疾病病例详情 Mock 数据

**用户故事：** 作为一名开发者，我希望每位患者都有对应的疾病病例详情数据，以便验证各疾病表单的数据读写正确性。

#### 验收标准

1. WHEN 执行 Mock 数据脚本 THEN 系统 SHALL 为每位患者创建对应疾病类型的病例详情记录（7 张疾病子表各有数据）：

   - **DSD 病例**（`dsd_case` 表）：包含性别发育异常相关字段（染色体核型、性腺情况等）
   - **FSS 病例**（`fss_case` 表）：包含遗传性骨病相关字段（骨龄、身高 SDS 等）
   - **CPP 病例**（`cpp_case` 表）：包含性早熟相关字段（初诊年龄、骨龄超前年数等）
   - **MAS 病例**（`mas_case` 表）：包含 McCune-Albright 相关字段（皮肤咖啡斑、骨纤维异常增殖等）
   - **SGA 病例**（`sga_case` 表）：包含小于胎龄儿相关字段（出生体重、出生身长等）
   - **SSS 病例**（`sss_case` 表）：包含家族性矮小相关字段（父母身高、遗传靶身高等）
   - **ELTM 病例**（`eltm_case` 表）：包含 E路童萌相关字段

2. WHEN 查询某患者的病例详情 THEN 系统 SHALL 返回该患者对应疾病类型的完整病例字段，且字段值在合理的医学范围内（如身高 80～180cm，体重 10～80kg）
3. WHEN 查询不存在的病例 THEN 系统 SHALL 返回 404 错误，而非空数据

### 需求 5：随访记录 Mock 数据

**用户故事：** 作为一名开发者，我希望患者有多条随访记录，以便验证随访管理和生长曲线展示的正确性。

#### 验收标准

1. WHEN 执行 Mock 数据脚本 THEN 系统 SHALL 为每位患者创建 3～5 条随访记录（`patient_follow_up` 表），随访时间间隔约 3～6 个月

2. WHEN 查询某患者的随访列表 THEN 系统 SHALL 每条随访记录包含以下字段：
   - 随访日期（按时间顺序排列）
   - 身高（cm，随时间递增，模拟儿童生长趋势）
   - 体重（kg，随时间递增）
   - BMI（根据身高体重计算）
   - 骨龄（岁）
   - 随访医生 ID

3. WHEN 查询 MAS 患者的随访记录 THEN 系统 SHALL 同时返回 `mas_follow_up` 表中的 MAS 专属随访字段
4. WHEN 按时间范围筛选随访记录 THEN 系统 SHALL 返回该时间范围内的随访记录，数量与 Mock 数据一致
5. WHEN 查看患者生长曲线 THEN 系统 SHALL 能基于多条随访数据绘制出有意义的生长趋势图（数据点 ≥ 3 个）

### 需求 6：Mock 数据脚本工程化

**用户故事：** 作为一名开发者，我希望 Mock 数据以结构化的 SQL 脚本形式提供，以便一键初始化和反复验证。

#### 验收标准

1. WHEN 查看 Mock 数据脚本目录 THEN 系统 SHALL 包含以下文件结构：
   ```
   eksjk_v2/scripts/mock/
   ├── README.md                   # 说明文档（账号列表、执行方式）
   ├── init-mock-data.sh           # 一键初始化脚本
   ├── clean-mock-data.sh          # 一键清理脚本
   └── sql/
       ├── 01_hospitals.sql        # 医院数据
       ├── 02_users.sql            # 用户账号数据（含 BCrypt 密码）
       ├── 03_patients.sql         # 患者基础信息（21+ 条）
       ├── 04_disease_cases.sql    # 7 种疾病病例详情
       └── 05_follow_ups.sql       # 随访记录数据
   ```

2. WHEN 执行 `init-mock-data.sh` THEN 系统 SHALL 按 `01 → 05` 的顺序依次执行 SQL 文件，完成全量数据初始化
3. WHEN 重复执行 `init-mock-data.sh` THEN 系统 SHALL 不报错（所有 SQL 使用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE` 保证幂等性）
4. WHEN 执行 `clean-mock-data.sh` THEN 系统 SHALL 清除所有 Mock 数据（按外键依赖逆序删除），恢复空库状态
5. WHEN 查看 `README.md` THEN 系统 SHALL 包含：
   - 所有测试账号的用户名、密码、角色说明
   - 脚本执行前置条件（MySQL 连接信息配置方式）
   - 各 SQL 文件的数据说明
6. WHEN 查看 SQL 文件 THEN 系统 SHALL 每条 INSERT 语句包含中文注释，说明该条数据的测试用途
