## 1. 问题现象

本地 `eksjk_db` 已完成 datamain 全量同步，数据校验通过（5354 名患者、3626 条知情同意、5296 次体征测量等），但前端表现为：

| 页面区域 | 现象 |
|----------|------|
| ELTM 病例列表 | 姓名、性别、年龄、病例编号、医院、签署状态有值；**身高、体重、BMI、主诉、病历号、医生列为空** |
| 详情 - 基本信息 | 姓名、性别、出生日期、电话、身份证、医院有值；**病历号、身高、体重、BMI、主诉、地址等为空** |
| 详情 - 基线临床信息 | 全部为空 |
| 详情 - 基线辅助检查 | 全部为空 |
| 详情 - 遗传学检查 | 全部为空 |
| 详情 - 随访记录 | 显示“暂无随访记录” |
| 详情 - 诊断 | 全部为空 |
| 详情 - 知情同意书 | 即使有签署记录，也显示为空白条目，无文件名、无可用下载地址 |

---

## 2. 结论先行

**同步没有失败，问题在于“数据落了库，但页面没有读”**，可归纳为四类原因：

1. **前端读的是旧临床模型**：详情页所有 Tab 绑定的是 `datamain_patient` 主表字段、`datamain_patfoll` 随访表、`datamain_szfyeltm` ELTM 子表，而本次同步把明细写进了 16 张新的 `eltm_*` 表，前端没有任何接口或组件读取这些新表。
2. **同步只白名单写入患者主表 8 个字段**：姓名、性别、生日、电话、身份证、医生、医院、创建时间。身高/体重/主诉/病历号等旧字段从未写入。
3. **知情同意书存在字段映射缺失**：同步写入了 `pdf_file_name`、`pdf_path`、`content`，但 `InformedConsentVO` 只暴露旧的 `fileName`/`ossUrl`，前端也只读这两个字段，因此内容可见但“空壳”。
4. **列表“医生”列存在覆盖 Bug**：列表查询没有查询 `doctor_name`，且 `convertToVO` 会用 `consent.getDoctorName()`（全为 null）覆盖患者主表的有效医生名。

此外，**部分空白属于外部数据源本身缺失**，例如 cxList 没有病历号、诊断、治疗方案、实验室检查明细，随访也不是逐次返回。这类字段无论怎么改前端都不会有值，需要明确区分“待修复”与“源数据没有”。

## 3. 逐项根因分析

### 3.1 详情页 Tab 的数据来源错位（核心原因）

`CaseDetail.vue` 的加载逻辑：

- `eksjk_v2/eksjk-frontend/src/views/case/CaseDetail.vue:1155` `loadDetail()` 只调用 `GET /api/patients/{id}`；
- 该接口 `PatientServiceImpl.getDetail()`（`eksjk_v2/eksjk-backend/eksjk-service/src/main/java/com/eksjk/service/impl/PatientServiceImpl.java:202`）只返回：
  - `datamain_patient` 主表字段；
  - `datamain_szfyeltm` ELTM 子表（`loadDiseaseData` 的 `case "10000007"`，第 526 行）；
  - 染色体核型表。
- 随访 Tab 由 `FollowUpList.vue:178` 调用 `getFollowUpList`，读的是 `datamain_patfoll`；
- 知情同意 Tab 由 `InformedConsentList.vue:47` 调用 `/api/informed-consent/list-by-patient`。

本次同步的数据实际落在：

| 新表 | 行数 | 有数据的患者数 | 前端是否读取 |
|------|------|----------------|--------------|
| `eltm_patient_profile` | 5354 | 5354 | 否 |
| `eltm_hospital_bind` | 4107 | 3730 | 否 |
| `eltm_project` | 4028 | 3835 | 否 |
| `eltm_form_submission` | 2561 | 380 | 否 |
| `eltm_form_answer` | 24098 | - | 否 |
| `eltm_patient_pic` | 759 | 181 | 否 |
| `eltm_physical_record` | 5296 | 2347 | 否 |
| `eltm_physical_item` | 78059 | 2347 | 否 |
| `eltm_assessment_report` | 69 | 37 | 否 |
| `eltm_exercise_record` / `summary` | 1 / 1 | 1 | 否 |
| `eltm_sleep_record` / `summary` | 1 / 1 | 1 | 否 |
| `informed_consent`（sign 记录） | 3626 | 3242 | 部分读取 |

**结论：明细数据完整存在于数据库，但前端没有消费入口。**

### 3.2 患者主表只写入了 8 个字段

`DatamainSyncTxService.applyRowFields()`（`eksjk_v2/eksjk-backend/eksjk-service/src/main/java/com/eksjk/service/sync/DatamainSyncTxService.java:129-173`）只写入：

```
name、sex、birth_time、self_tel/contacts_num、idcard/card、
doctor_name、hospital_name、c_time
```

因此以下旧字段全部为空：

| 字段 | 本地实测结果 |
|------|--------------|
| `height` | 5354 条全部为空 |
| `weight` / `bmi` | 5354 条全部为空 |
| `medrec_num`（病历号） | 5354 条全部为空 |
| `chi_com`（主诉） | 5354 条全部为空 |
| `fir_vis_time`（初诊时间） | 5354 条全部为空 |
| 基线辅助检查、遗传、诊断字段 | 5354 条全部为空 |

其中 **身高/体重/BMI 是可以补的**：`eltm_physical_item` 中已有 `height:Tab`（5146 条）、`weight:Tab`（5148 条）、`bmi`（5145 条），覆盖 2347 名患者。`medrec_num`、主诉、诊断、治疗方案在 cxList 中确实没有对应字段，属于源数据缺失。

### 3.3 随访记录为空

`FollowUpList.vue` 读取的是 `PatientFollowUp`（表 `datamain_patfoll`）。实测：

```sql
SELECT COUNT(*) FROM datamain_patfoll f
JOIN datamain_patient p ON f.patient_id = p.id
WHERE p.external_id IS NOT NULL;
-- 0
```

同步写入的是 `eltm_physical_record` + `eltm_physical_item`（EAV 结构）和 `eltm_form_submission`，没有投影到旧随访表。

### 3.4 知情同意书“有记录但显示为空”

数据库实测（`sign_id IS NOT NULL`）：

| 字段 | 有值数量 |
|------|----------|
| 总记录 | 3626 |
| `sign_time` | 3137 |
| `doctor_name` | **0** |
| `file_name` | **0** |
| `oss_url` | **0** |
| `content` | **5**（仅抽样补拉） |
| `patient_sign_image` | 3 |
| `pdf_file_name` | 1 |

原因链：

1. `DatamainDetailParser.parseConsents()`（`DatamainDetailParser.java:303-333`）只写签署基础字段，**不写 `doctor_name`、`file_name`、`oss_url`**；
2. `DatamainConsentBackfillService`（`DatamainConsentBackfillService.java:118-119`）补拉时写入的是 **`pdf_path`、`pdf_file_name`**，不是旧字段；
3. `InformedConsentVO`（`eksjk_v2/eksjk-backend/eksjk-model/src/main/java/com/eksjk/model/vo/InformedConsentVO.java:14-32`）只暴露 `fileName`、`ossUrl`，**没有 `pdfFileName`、`pdfPath`、`content`、`signStatus`**；
4. `InformedConsentServiceImpl.listByPatientId()` 用 `BeanUtils.copyProperties` 转换，VO 没字段，值直接丢弃；
5. 前端 `InformedConsentList.vue` 模板读 `file.fileName`，下载读 `file.ossUrl`，自然全空。

另外，正文/PDF 只对 5 条做了抽样补拉，**其余 3621 条从未调用 `getzqbyid`**，即使前端字段修好，大多数记录仍然只有签署时间。

### 3.5 列表“医生”列为空（独立 Bug）

`PatientServiceImpl.queryPage()` 的列表查询列（同文件第 85-90 行）**没有 select `doctor_name`**：

```java
wrapper.select(Patient::getId, Patient::getCaseNum, Patient::getName, Patient::getSex,
        Patient::getAge, Patient::getAgeY, Patient::getAgeM, Patient::getMedrecNum,
        Patient::getHeight, Patient::getWeight, Patient::getBmi, Patient::getChiCom,
        Patient::getIcd, Patient::getDisClass, Patient::getImpPer, Patient::getCTime,
        Patient::getHospitalName, Patient::getAuditStatus, Patient::getDiagnosisStatus,
        Patient::getDelFlg);
```

同时 `convertToVO()`（第 462、484-490 行）主动排除 `doctorName`，再用 `consent.getDoctorName()` 覆盖：

```java
BeanUtils.copyProperties(patient, vo, "id", "doctorName");
...
vo.setInformedConsentStatus("signed");
vo.setDoctorName(consent.getDoctorName());   // 全表为 null，覆盖了 patient.doctor_name
```

而患者主表中 5354 条 `doctor_name` **全部有值**。这是同步数据被前端“反向覆盖”的典型问题。

### 3.6 ELTM 子表几乎是空的

`loadDiseaseData` 对 ELTM 读取 `datamain_szfyeltm`，实测该表只有 6 行，且只对应 6 名同步患者。ELTM 的临床字段（既往史、发育史等）设计在旧子表中，本次同步并未写入。

### 3.7 按现有 Tab 逐模块核对

结论：**外部数据没有丢失，全部已落库；但它们是"表单 JSON + 体征 EAV"形态，没有映射到现有页面读取的旧字段/旧表。**

| 现有 Tab | 外部是否存在 | 已同步位置 | 覆盖量 | 页面为空的原因 |
|----------|--------------|------------|--------|----------------|
| 基线-临床信息 | 是 | `eltm_form_submission` / `eltm_form_answer`；`eltm_physical_record` / `eltm_physical_item` | 基线临床症状和体征 331 份、体格检查 273 份、病史 141 份、人口学信息 146 份、GH 用药记录 311 份；体征测量 5296 次 / 2347 人 | 页面读 `datamain_patient` 临床列和 `datamain_szfyeltm`；同步未做表单→临床字段映射 |
| 基线-辅助检查 | 是 | 同上（表单表） | 实验室检查 282 份、影像学结果 248 份、其他检查类合计 848 份 / 177 人 | 页面读患者主表 `lh/fsh/e2/...` 平铺字段；表单未解析到这些列 |
| 遗传学检查 | 是 | 同上（表单表） | 基因结果 9 份、染色体结果 9 份、其他基因/染色体检查 2 份，共 20 份 / 15 人 | 页面读 `patient_genetics` 和 `diseaseData`；外部数据在表单里，未映射 |
| 随访记录 | 部分有 | `eltm_physical_record` / `item` + 表单表 | 体征测量 5296 次 / 2347 人；随访类表单 26 份 / 24 人 | 页面读 `datamain_patfoll`（已同步患者的记录数为 0）；体征和表单未投影为随访记录 |
| 诊断 | 很少 | 表单表 + `eltm_assessment_report` | 诊断相关表单 4 份 / 4 人（含"主要转归和诊断" 1 份）；评估报告 69 份 / 37 人 | 页面读患者诊断字段和 `datamain_szfyeltm`；外部没有结构化诊断/治疗方案，只有少量表单和报告结论 |
| GH 不良事件 | 是 | 表单表 | 不良事件 11 份、不良反应收集 1 份，共 12 份 / 11 人 | 页面读 `datamain_gh_adverse_event`（匹配同步患者的记录数为 0）；不良事件在表单里，未映射 |
| 知情同意书 | 是 | `informed_consent` | 3626 条 / 3242 人 | 已同步；但 VO 字段映射缺失、正文只补拉 5 条、PDF 基本未补拉 |

需要特别说明：

- 外部表单不是"无结构文本"，`original_data` 里包含题目 key、答案值以及选择题的 `labelList`（选项文案），可以还原和展示；
- 但它和内部临床字段不是一一对应关系。要填满现有 Tab，必须逐个表单做字段映射，而不是简单"同步一下"；
- "诊断"模块本质上是内部医生的诊疗工作流，外部只提供少量评估结论，不能等同于内部诊断；
- "随访记录"外部是"多次体征测量 + 若干随访表单"，不是内部 132 列的完整随访结构。

## 5. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A. 新表直出 | 新增 ELTM 专属 API 与详情 Tab，直接读 `eltm_*` | 数据完整、无需污染临床表、可只读展示 | 需要前后端开发工作量 | **推荐作为主方案** |
| B. 回填旧模型 | 把外部数据写进 `datamain_patient` 临床列、`datamain_patfoll`、`datamain_szfyeltm` | 现有页面立即可用 | 字段语义不一致、破坏审核/诊断流程、随访列只有 132 列仍装不下表单 | 不推荐全量采用 |
| C. 混合 | P0 修显示 Bug + 回填少量摘要字段；P1 新增 ELTM 只读 Tab | 快速见效且长期结构正确 | 需要分阶段实施 | **推荐** |

**推荐方案 C，分三阶段：**

- **P0（当天）**：修医生列、修知情同意字段映射、回填最新身高/体重/BMI、调整 ELTM 列表空列。
- **P1（1-2 天）**：新增 ELTM 专属详情 Tab，展示体征、表单、图片、报告、项目/医院。
- **P2（随后）**：批量补拉知情同意正文/PDF、签名图片入对象存储、必要时把表单里的实验室数据映射为临床字段。

### 6.4 回填患者主表最新身高/体重/BMI

**推荐写入同步逻辑**：在 `DatamainSyncTxService.syncPatient()` 的 `replacePhysical()` 之后，查最近一次测量并更新主表：

```sql
-- 一次性回填 SQL（也可放在同步代码中执行）
UPDATE datamain_patient p
JOIN (
    SELECT r.patient_id,
           MAX(CASE WHEN i.attribute_code = 'height:Tab' THEN i.attribute_value END) AS height,
           MAX(CASE WHEN i.attribute_code = 'weight:Tab' THEN i.attribute_value END) AS weight,
           MAX(CASE WHEN i.attribute_code = 'bmi'        THEN i.attribute_value END) AS bmi
    FROM eltm_physical_record r
    JOIN eltm_physical_item i ON i.record_id = r.id
    JOIN (
        SELECT patient_id, MAX(measure_time) AS mt
        FROM eltm_physical_record
        GROUP BY patient_id
    ) latest ON latest.patient_id = r.patient_id AND latest.mt = r.measure_time
    GROUP BY r.patient_id
) x ON x.patient_id = p.id
SET p.height = COALESCE(x.height, p.height),
    p.weight = COALESCE(x.weight, p.weight),
    p.bmi    = COALESCE(x.bmi, p.bmi)
WHERE p.external_id IS NOT NULL;
```

覆盖 2347 名有体征数据的患者；其余 3007 名外部数据本身没有体征记录，列表仍显示为空，这是正常的。

## 7. P1：ELTM 专属详情 Tab（核心交付）

### 7.1 设计原则

- 只读展示，明确标注“数据来源：E路童萌”；
- 不影响 DSD/FSS/CPP 等现有病种页面；
- ELTM 详情只保留“基本信息 + 知情同意书”两个旧 Tab，其余替换为外部数据 Tab；
- 所有分页接口按 `measure_time` / `submitted_at` 倒序，默认每页 20 条。

### 7.2 后端 API

新增 `EltmPatientDataController`（建议放在 `eksjk-web/.../controller/`），全部 `@SaCheckLogin`，并校验患者数据权限。

## 8. P2：数据完善与长期优化

### 8.1 批量补拉知情同意书正文/PDF

现状：3626 条签署记录中仅 5 条有正文，1 条有 PDF。建议：

- 新增定时任务或手动入口，遍历 `informed_consent` 中 `sign_id IS NOT NULL AND content IS NULL` 的患者；
- 每个患者调用一次 `getzqbyid`（不是每条 sign 调一次）；
- 限速 2 请求/秒，失败写 `eltm_sync_error`，支持断点续跑；
- 补拉后更新 `content`、`pdf_path`、`pdf_file_name`、`patient_sign_image`、`pdf_status`；
- 预览/下载时若仍为空，可按需实时调用一次补拉接口。

### 8.2 签名图片入对象存储

`getzqbyid` 的监护人/医生签名可能是 base64，当前超过 500 字符直接丢弃。建议：

- 新增上传服务，把 base64 转存到 OSS/S3；
- `informed_consent` 中保存对象 URL，而不是内联 base64；
- 同步/补拉时只保存 URL，避免行过大。

### 8.3 表单答案可读化

`eltm_form_answer` 的 `field_label` 当前为空，`field_key` 是外部题目的随机 key（如 `single1722427836555`）。不过 `original_data` 中带有选择题的 `labelList`，可以把选项值还原成中文文案，因此数据本身不是不可读的。建议：

- 短期：展示表单名称、提交时间、评分、评估结论，详情抽屉按 `original_data` 渲染"题目 key + 答案值 + `labelList` 文案"；
- 中期：从外部表单定义中获取题目文案，建立 `field_key -> label` 映射表；
- 长期：把"实验室检查""体格检查"等结构化表单映射为内部辅助检查字段。

### 8.4 生长测量转随访视图（可选）

如业务方希望复用现有“随访记录”页的成长曲线：

- 提供一个只读适配接口，把 `eltm_physical_record` 映射为 `PatientFollowUp` 同形结构（`follTime`、`ht`、`wt`、`bmi`）；
- 前端 FollowUpList 对 ELTM 隐藏“编辑/删除”按钮；
- 不改旧表、不写入旧表，避免污染内部审核流程。

### 8.5 同步日志增加数据完整度指标

在 `eltm_sync_log` 或单独统计接口中增加：

- 有体征记录的患者数；

- 同意书正文覆盖率；
