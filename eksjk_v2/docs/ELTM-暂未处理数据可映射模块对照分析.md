# ELTM「暂未处理数据」可迁移模块对照分析

> 分析日期：2026-10-18
> 分析对象：ELTM 病例详情页「暂未处理数据」Tab 中的 6 组外部数据
> 目标模块：基本信息、基线-临床信息、基线-辅助检查、遗传学检查、随访记录、诊断、GH不良事件
> 数据口径：本地 `eksjk_db` 实测（5354 名 ELTM 患者、2561 份外部表单、5296 次体征测量）

---

## 1. 分析范围与数据基线

「暂未处理数据」当前分为 6 组：

| 分组 | 数据表 | 实测数据量 | 覆盖患者 |
|------|--------|-----------|----------|
| 外部表单 | `eltm_form_submission` / `eltm_form_answer` | 2561 份 / 24098 条答案 | 380 人 |
| 检查资料 | `eltm_patient_pic` | 759 张 | 181 人 |
| 评估报告 | `eltm_assessment_report` | 69 份 | 37 人 |
| 体征明细 | `eltm_physical_record` / `eltm_physical_item` | 5296 次 / 78059 条属性 | 2347 人 |
| 运动与睡眠 | `eltm_exercise_*` / `eltm_sleep_*` | 各 1 条 | 1 人 |
| 项目与医院 | `eltm_project` / `eltm_hospital_bind` | 4028 / 4107 条 | 3835 / 3730 人 |

外部表单共 92 种表单名称、大量表单模板（同一表单名在不同项目下 `form_key` 不同）。其中与 7 个目标模块**存在结构化对应关系**的候选表单合计 **1260 份、228 名患者**（不含归入「知情同意书」模块的 99 份知情同意书上传表单）。

> **重要前提：** `eltm_form_answer.field_label` 实测全部为 NULL，外部表单没有题目文案。下文的字段语义来自「表单名称 + 取值范围 + 选项 labelList」推断；除已有人工映射（病史/染色体/基因）外，新增映射落地前必须取得外部表单定义逐题确认。

## 2. 结论摘要

### 2.1 优先迁移（字段语义相对明确、目标字段已存在）

| 来源 | 目标模块 | 核心内容 |
|------|----------|----------|
| 产妇信息收集（24 份/24 人） | 基本信息 + 基线-临床信息（家族史） | 出生体重、出生身长、孕周、分娩方式、胎次产次、父母身高/姓名/出生日期 |
| 人口学信息（146 份/145 人） | 基本信息 | 民族、家庭地址、出生日期、性别 |
| 病史（141 份/138 人，已映射 5 字段） | 基本信息 + 基线-临床信息 | 现病史、既往史、出生身长/体重、孕周已完成；剩余 2 个枚举字段待确认 |
| 体征明细（5296 次/2347 人） | 基线-临床信息 + 家族史 | 父母身高（2034 人）、身高 SDS（2129 人）；身高/体重/BMI 已映射 |
| 基因结果（9 份/9 人） | 遗传学检查 + 基本信息 | 基因名称已映射；检测方法、位点、类型、模式待补 |
| 染色体结果（9 份/8 人） | 遗传学检查 | 染色体核型已映射 |

> 注：产妇信息收集的出生体重/身长/孕周/胎次/产次/父母身高等字段语义按取值范围推断；其中**分娩方式已由选项 labelList（自然分娩/剖宫产）确认**，其余是/否类单选需按表单定义确认。

### 2.2 有条件迁移（结构可对应，需要新增投影逻辑或转存附件）

| 来源 | 目标模块 | 前置条件 |
|------|----------|----------|
| GH用药记录（311 份/152 人） | 基线-临床信息-诊疗方案 / 随访记录 | 需确认"当前方案"与"历史记录"的取舍规则；诊疗方案是 JSON 结构，不能用通用字段映射 |
| 不良事件 + 不良反应收集（12 份/11 人） | GH不良事件 | 需实现 `ADVERSE` 投影（当前代码未实现）；选项需做枚举字典转换 |
| 合并用药记录（251 份/139 人） | 随访记录-其他用药 | 子表多行，需转成文本或明细，并新建随访记录 |
| 体格检查（273 份/109 人，另有儿童体格检查 2 份/2 人） | 基线-临床信息 / 随访记录 | 与体征明细重复，需要去重规则；**该表单几乎没有检查日期（仅 1 个 date 字段/4 条答案），难以按日期归入随访** |
| 检查资料图片（759 张/181 人） | 基线-辅助检查-影像资料上传 | 外部图片 403（已实测），需后端代理或转存 |
| 实验室检查/影像学结果（主模板） | 基线-辅助检查-附件 | **主模板只有图片、没有数值**，只能做附件 |
| 专项实验室/指标表单（糖尿病指标、血常规、血糖、IGF-1 等） | 基线-辅助检查 / 随访记录 | 含结构化数值，但需先确认题目与单位 |
| 其他检查（骨龄 X 线、垂体 MRI/CT） | 基线-辅助检查 | 可补骨龄/垂体 MRI 字段，样本各 1 份 |
| 出生史 | 基本信息 | 孕周/出生身长/出生体重等，1 份 |
| 术后辅助治疗 | 诊断 / 诊疗方案 | 12 个输入 + 8 个单选，1 份 |
| 体征附件 URL（4 类，各 991 人） | 基线-辅助检查-附件 | 同上，需转存 |
| 主要转归和诊断（1 份） | 诊断 | 数据几乎为空，优先级低 |

### 2.3 建议保留在「暂未处理数据」

- 全部量表/问卷（营养调查、ADL、SDS、睡眠问卷、Piers-Harris、DDST、GESELL、CBQ、孤独症早筛等）
- 评估报告（69 份，均为量表评估模型，不是临床诊断结论）
- 运动与睡眠（各 1 条，无对应模块）
- 项目与医院（患者主表已同步医院/医生，仅作溯源）
- 主实验室检查/影像学结果表单中的图片（只有图片，无结构化数值；若纳入则作为附件而非数值字段）
- 基线临床症状和体征等自由文本症状清单（无精确对应字段，保留原文更安全）
- 基本信息填写、患者基线信息、首诊病史询问中的园所/演示类数据

### 2.4 归入前序其他模块（不在本次 7 个模块清单内）

| 来源 | 目标模块 | 覆盖量 | 说明 |
|------|----------|--------|------|
| 知情同意书上传 | 知情同意书 | 99 份/99 人 | 可关联/合并到现有 `informed_consent`，与签署记录去重 |

## 6. 实施建议

1. **沿用现有映射表机制**：新增字段只需向 `eltm_form_field_mapping` 插入 `form_key + field_key → target_scope.target_field` 配置，不改代码。多模板表单（人口学信息 12 个模板、GH 用药 12 个模板、体格检查 12 个模板）需要逐模板配置。
2. **补齐投影代码的 scope**：
   - 现有代码支持 `PATIENT` / `ELTM_CASE` / `GENETICS`；
   - `FOLLOWUP` / `ADVERSE` 仅在表注释中预留，代码未实现，需要新增投影器；
   - 家族史、附件、随访问卷需要新增 `FAMILY_MEMBER`、`ATTACHMENT`、`FOLLOWUP` 等 scope 或独立服务。
3. **补齐枚举字典转换**：现有 `transform_rule` 只有 `WEIGHT_G_TO_KG` / `BIRTH_HEIGHT_CM` / `GEST_WEEK` / `TEXT_CLEAN`，没有"中文选项 → 内部编码"的转换。分娩方式（自然分娩/剖宫产 → 0/1）、不良事件严重程度/关联性等必须先加字典转换，否则写入的中文不会匹配内部下拉框。
4. **投影原则保持不变**：只填空、不覆盖本地值；同一目标字段取最近一次非空提交；多记录目标（随访、不良事件）以 `form_data_id` 做幂等，避免重复同步。
5. **附件类数据先解决防盗链**：外部图片直连已实测返回 **HTTP 403**，需要后端代理下载后转存到本地对象存储/文件服务，再挂到「影像资料上传」。文件上传组件支持图片、PDF、DICOM。
6. **诊断模块不建议自动投影**：外部只有量表结论和 1 份近乎空的转归表单，自动写入会干扰内部诊断/审核流程；如需要，只做只读参考展示。
7. **对医生工作流的影响**：外部同步的随访/不良事件建议标记 `data_source=ELTM_SYNC`，前端只读，不进入审核发放队列（随访记录已有此机制，GH 不良事件需补充同类标记）。
8. **两个已发现的代码级前置问题**：
   - `CaseDetail.vue` 的 `EXAM_FIELDS` 未包含 `bloodRoutine`、`urineRoutine`、`hepatitisB`、`liverKidneyElectrolyte`。这 4 个字段在 `Patient` 实体和 `BaselineExamForm` 中都存在，但详情加载时不会进入 `examData`；且组件编辑后会把默认值 `'0|'` 回写到 `examData`。**在把血常规/尿常规等结构化检验映射进去之前，必须先补齐该列表**，否则会出现"不显示"甚至"保存后被置为未查"。
   - 家族史保存为 `Patient.familyMembers` JSON；父母身高不能在映射表中直接按字段赋值，需要专用合并逻辑。诊疗方案同理，实际存于 `EltmCase.diaTreaPlan`（JSON 字符串），通用 `setIfBlank` 无法写入结构化方案。

## 8. 最终判断

**「暂未处理数据」并不是全部都无法处理：**

- **约 1260 份表单、228 名患者**存在可迁移到前面模块的结构化数据，优先做「产妇信息收集 + 人口学信息 + 体征父母身高/SDS」即可用最小成本显著改善基本信息与基线-临床信息。
- **GH用药记录、不良事件**是下一个高价值批次，但需要扩展投影代码与幂等规则。
- **主「实验室检查」「影像学结果」与检查资料图片**只能作为附件，不能填补数值型辅助检查字段，需要先解决外部图片 403；少量专项实验室表单含结构化数值，可作为补充。
- **诊断、量表问卷、评估报告、运动睡眠**不建议迁移，保留在「暂未处理数据」更符合现有业务语义与审核流程。

  - 知情同意书上传 → 知情同意书记录；
  - 骨龄、垂体 MRI/CT → 基线-辅助检查；
  - 主要转归和诊断、术后辅助治疗 → 诊断/治疗方案。
- `EltmProjectionTxService`：新增 `ENUM:` 字典转换、`FAMILY` scope、调用扩展迁移服务。
- 新增 `EltmAttachmentService`：带 `Referer: https://eksf.zsmm.org.cn/` 下载外部图片到本地文件存储，写入文件备注，回填知情同意书/随访附件路径。
- 新增接口：
  - `POST /api/eltm/attachments/run`（全量附件迁移）
  - `POST /api/eltm/attachments/patient/{id}`（单患者附件迁移）

**前端**

- `CaseDetail.vue`：`EXAM_FIELDS` 补齐 4 个检验字段；
- `FileUpload.vue`：只加载 `image` 分类，避免知情同意书图片混入基线辅助检查；
- `InformedConsentList.vue`：支持本地附件通过带 token 的 blob 方式下载。

### 10.3 复跑方式

```bash
# 1. 应用迁移（本地）
mysql -u eksjk -peksjk123 --default-character-set=utf8mb4 eksjk_db < eksjk_v2/init-sql/34-eltm-migration.sql

# 2. 安装后端模块（jacoco 覆盖率校验会拦截，需跳过）

```

### 10.4 已知限制

- 外部表单 `field_label` 为 NULL，人口学/产妇/体格检查的字段语义部分依赖取值范围推断；如后续拿到表单定义，可进一步校正。
- GH 用药记录按每次提交生成一条只读随访（311 条），摘要为文本；未写入结构化 `diaTreaPlan` JSON。
- 实验室检查/影像学结果主模板只有图片，已作为附件迁移；专项实验室表单的结构化数值尚未逐项解析（缺少题目文案）。
- 不良事件的症状文本为表单原始文本汇总，部分记录含复合字段内容，医生可在只读记录中查看。
- 附件迁移仅在 `storage-type=local` 时生效；生产 S3/OSS 模式需接入对象存储上传。
- 5 个附件下载失败，可通过 `POST /api/eltm/attachments/patient/{id}` 单患者重试。
